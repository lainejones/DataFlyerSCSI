# dataflyer.device audit, 2026-10-31 (1.0.4, main @ 6733c3b)

This is a read-only review of `dev/dataflyer.c`, `dev/ide.c`, `dev/start.S` and `dev/dataflyer.h`, plus
`tools/rdbmountcore.h`, which ships in the package. Nothing was built or run. I looked for the same
kind of problem as the vendor-CDB bug fixed in 1.0.4: an assumption that holds for the common case only.
I also looked for robustness bugs.

Each finding gives the place, the assumption, what breaks it, the symptom, and a test that would show it.
The tests are meant for `flysuite`. Tags:

- **certain**: I read the code path end to end.
- **suspect**: it depends on target, drive or exec behaviour that the code cannot show.

The findings are ranked by likelihood x impact.

---

## High

### H1. One 10-second limit for every command, and no bus reset anywhere (certain)
**Where:**
- `dataflyer.c:70` (`T_REQ`)
- `dataflyer.c:355` (wait for REQ)
- `dataflyer.c:410-412` (give up and `chip_idle()` only)
- `dataflyer.c:194-197` (BSY still set: selection fails)
- `dataflyer.c:54` (`ICR_RST` is defined but never used)
- `dataflyer.c:828` (`CMD_RESET` is a no-op)

**Assumption:** every command reaches its next phase within 10 s, and a target that is still busy will
let go of the bus by itself.

**Breaks with:**
- FORMAT UNIT, including HDToolBox "Low-level format" on a real disk (minutes).
- SEND DIAGNOSTIC self-test.
- START STOP UNIT (start, IMMED=0) on an old full-height drive (15-30 s spin-up).
- TD_EJECT "load" on a slow CD drive.
- Tape REWIND, SPACE or ERASE.
- SYNCHRONIZE CACHE on a big cache.
- A scanner during a scan.

**Symptom:**
1. After 10 s the request fails with `HFERR_SelTimeout` (or `TDERR_NotSpecified`). The bus semaphore was
   held all that time, so IDE I/O stopped too.
2. The target is still connected and holds BSY. Every later command to **any** SCSI id fails after
   200 ms in `select_target`.
3. When the target finishes, it asserts REQ for STATUS. Nobody answers, so the bus stays hung until the
   power is cycled.

Nothing in the driver can recover: there is no RST pulse, and `CMD_RESET` does nothing.

**Test (flysuite):** `SLOWCMD`:
1. HD_SCSICMD START STOP UNIT stop (`1B 00 00 00 00 00`), then start with IMMED=0, on a real mechanical disk.
2. Time the start.
3. Right after it, send TEST UNIT READY to another id. That must still work.

Optionally, FORMAT UNIT on a scratch real disk. Also a "recovery" test: after any request that fails
with a bus error, check that INQUIRY to every other present id still works.

**Fix direction:**
- Make the REQ wait per-command or unbounded while BSY is held. HD_SCSICMD could take a caller-set
  timeout, or use a long default for opcodes $04/$1D/$1B/$01/$19/$35.
- Pulse RST (ICR bit 7, at least 25 us) when BSY is stuck at selection or after a mid-command timeout.
- Make `CMD_RESET` do that too.
- Handle the UNIT ATTENTION that follows (see H5).

### H2. ATAPI data loop: direction not checked, and no overall bound (certain code; device side suspect)
**Where:** `ide.c:296-329`, plus the inner loop at `ide.c:301-307`.

**Assumption:** the device's data phase always goes the way the caller's `out` flag says, and DRQ
always comes with a non-zero byte count. The loop never reads the interrupt-reason I/O bit
(`I_COUNT` bit 1).

**Breaks with:** HD_SCSICMD on an IDE ATAPI unit (101, or scsi.device unit 1 after the takeover) with
the wrong direction flag. This is a common caller bug: INQUIRY or MODE SENSE sent with `scsi_Flags = 0`
(SCSIF_WRITE), or MODE SELECT sent with SCSIF_READ. Each pass then reads (or writes) the data port while
the device expects the opposite. DRQ and the byte count stay as they are, and `for (;;)` goes round
forever. A DRQ with a byte count of 0 does the same.

**Symptom:** a permanent hang that never counts as a timeout:
- The driver task spins at priority 1 without sleeping.
- It holds `buslock`, so all dataflyer.device and scsi.device I/O stops.
- Tasks at priority 0 get almost no CPU.

Separately, the inner `for (t = T_BUSY; ...)` loop can spin 14 million times (20+ s) with plain CIA
reads and never calls `df_pause`.

**Test:** `ATAPIDIR`. Run it on WinUAE `winuae-DataFlyer-test-CD.uae`, or on any IDE ATAPI drive:
1. Send HD_SCSICMD INQUIRY (alloc 36) to unit 101 with `scsi_Flags = 0`.
2. Issue it with SendIO from a child task, wait at most 15 s, and report HANG if it has not come back.

Expected: an error or a short transfer within a second. Repeat with MODE SENSE(6) page $3F and
`flags = 0`. A third variant: MODE SELECT with SCSIF_READ.

**Fix direction:**
- Take the direction from the interrupt reason (I/O = 1 means device-to-host).
- On a mismatch, or a zero byte count, drain or pad and then fail.
- Give the whole command one time budget.

### H3. 256-byte blind runs are chosen by opcode alone (certain code; the CPU hold is documented)
**Where:**
- `dataflyer.c:433-434` (`blockxfer` = opcode in {08,28,A8,0A,2A,AA} and `len % 512 == 0`)
- `dataflyer.c:279-290`
- `start.S:73-84` (and `start.S:154-165` for writes)

**Assumption:** a READ(6)/(10)/(12) always returns whole 512- or 2048-byte blocks, so a run of 256 never
ends early. The comment at `dataflyer.c:272-276` says that a blind read of a byte that never comes
"holds the bus for good". The read happens with interrupts `Disable()`d, so no timeout can run.

**Breaks with:** any target whose data for such an opcode is not a multiple of 256 and is shorter than
`scsi_Length`:
- **Tape** (`READ(6)` 0x08 in variable-block mode: record length is less than the buffer).
- **Scanners** (type 6, `READ(10)` 0x28 with a byte count; the last read is short).
- A CD set to 2352/2340/2336-byte blocks by MODE SELECT, as CD-DA rippers do.
- Disks formatted with 520/528-byte sectors (cheap surplus array drives).
- Any HD_SCSICMD whose `scsi_Length` (a multiple of 512) is larger than the CDB's blocks x block size,
  when that size is not a multiple of 256.

These are the same kind of assumption as the 1.0.4 bug: an opcode means "block read" only on
direct-access devices.

**Symptom:** a hard freeze of the whole machine. The CPU is stuck on a bus cycle with interrupts off.
No counter moves.

**Test:** `RUNEND`.
1. In WinUAE, set up a hardfile with a 520-byte (or 2352-byte) block size, if the emulated DataFlyer
   target accepts it. A ZuluSCSI with `BlockSize=520` should work too.
2. Send HD_SCSICMD `READ(10)` of 1 block with `scsi_Length = 1024`.
3. Then send 3 blocks with `scsi_Length = 2048`.

Expected: `scsi_Actual = 520` / `1560`, no freeze. Run it last, because the failure is a freeze.
A safe check that can always run: the same command on a 512-byte unit must return
`scsi_Actual = 512` (it ends on a run boundary).

**Fix direction:** use runs only when all of these hold:
- `un->devtype` is 0, 5, 7 or $0E;
- `un->bsize % 256 == 0`;
- the CDB's transfer length x `un->bsize == len`.

Use the byte-wise loop for everything else.

### H4. Block size falls back to 512 when READ CAPACITY fails, and the "first look" never clears it (certain)
**Where:**
- `dataflyer.c:614-616` (no capacity: `bsize = 512` and return 1)
- `dataflyer.c:653-654` (`rw` probes only when `bsize == 0`)
- `dataflyer.c:907-911` (`medium_in` clears `bsize` only when it was not the first look)

**Assumption:** a unit that is opened has its medium ready, or the medium's block size is 512 anyway.
This holds for the ZuluSCSI, which is ready at once.

**Breaks with:** a real CD-ROM or 2048-byte MO drive that is opened while the disc is still spinning
up. Three back-to-back READ CAPACITY tries, with no delay between them, all get NOT READY, so
`bsize = 512`. The same happens with no disc in at open, if the first `TD_CHANGESTATE` or poll comes
only after the disc is in. That first `medium_in` is the "first look", so `bsize` stays 512.

**Symptom (CD):** `rw` computes LBA = offset/512 and asks for `len/512` blocks. The drive treats these
as 2048-byte blocks:
- it reads the wrong sectors (4x too far);
- it sends 4x the data; the extra is drained byte by byte, which is slow;
- the request ends with **status GOOD and wrong data**.

The CD is unreadable until it is ejected and put back in.

**Symptom (2048-byte MO):** writes go to the wrong LBA and are padded with zeros (see H6), which
corrupts the disk.

**Test:** `CDLATE`.
1. Open the CD unit with no disc in. Do not call TD_CHANGESTATE.
2. Insert a disc (WinUAE: CD image change).
3. Wait 5 s.
4. Read 2048 bytes at offset 16*2048 with CMD_READ and check for `CD001` at byte 1.
5. Also check `TD_GETGEOMETRY`'s `dg_SectorSize` before and after.

Real-hardware variant: power on with a disc in a real CD drive and mount at boot.

**Fix direction:**
- When READ CAPACITY fails, leave `bsize = 0` (unknown).
- Have `rw` fail with `TDERR_DiskChanged` (or TDERR_NoDisk) while it is unknown.
- In `medium_in`, clear `bsize` when a medium is seen and `blocks == 0`, even on the first look.
- Leave a short delay between the probe's READ CAPACITY retries.

### H5. `rw` maps errors to the wrong codes, and UNIT ATTENTION is not retried (certain)
**Where:** `dataflyer.c:675-681`.

**Assumption:** a write that fails was refused because of write protection; a read that fails had a
bad sector.

**Breaks with:**
- On writes, these all become **`TDERR_WriteProt`**:
  - any status other than CHECK CONDITION (BUSY $08, RESERVATION CONFLICT $18, TASK SET FULL $28);
  - every sense key other than 3/6/7: NOT READY 2, HARDWARE ERROR 4, ILLEGAL REQUEST 5 (e.g. LBA past
    the end), ABORTED COMMAND $0B.
- On reads, NOT READY becomes `TDERR_BadSecSum` instead of a no-disk/changed error.
- Any UNIT ATTENTION fails the request with `TDERR_DiskChanged`, even on a fixed disk:
  - It happens after a target reset or power glitch, or after H1's fix sends a bus reset.
  - The request is not retried.
  - `changes++` is counted, but the change interrupts are never `Cause()`d. The UA has been used up,
    so the next poll sees nothing new.

**Symptom:**
- "Volume ... is write protected" requesters for faults that have nothing to do with protection.
- Spurious "disk changed" on fixed disks.
- A file system that relies on change interrupts misses a swap that `rw` saw first.

**Test:** `ERRMAP`:
- `CMD_WRITE` and `TD_WRITE64` of 1 block at offset = capacity x bsize (past the end). Expect
  `TDERR_SeekError` or `TDERR_NotSpecified`, not `TDERR_WriteProt` (28).
- `CMD_READ` at the same place.
- On a ZuluSCSI removable or CD with the medium ejected: `CMD_WRITE` / `CMD_READ`, expect no-disk or
  changed.
- UA path: after a bus reset (once H1 adds one) or a ZuluSCSI image swap, the first `CMD_READ` on a
  **fixed** unit must succeed.

### H6. Wrong-direction or over-long data phases: zeros go to the disk, and `scsi_Actual` reports bytes that did not move (certain)
**Where:**
- `dataflyer.c:373-389` (DATA OUT with `!out`, or past `len`: `put_byte(0)`; DATA IN with `out`:
  bytes dropped)
- `dataflyer.c:399/410/415` (`*actual = min(di, len)` counts those bytes too)

**Assumption:** the target's data phase matches `SCSIF_READ`, and it never wants more than
`scsi_Length`.

**Breaks with:**
- HD_SCSICMD `WRITE(10)` sent with SCSIF_READ: the driver happily writes **zero-filled blocks** to the
  medium.
- A WRITE whose CDB block count x block size is larger than `scsi_Length`: the rest is zero-padded
  onto the disk.
- INQUIRY sent with SCSIF_WRITE: status GOOD and `scsi_Actual = 36`, but the buffer is untouched.
- The H4 MO case: zero-padded writes.

**Symptom:** silent data destruction from a caller's flag bug; garbage parsed as valid data.

**Test:** `DIRMIS`:
1. On a scratch block (e.g. the flytest WRITE area at block 2048), write 0xAA.
2. Send HD_SCSICMD `WRITE(10)` of 1 block with `SCSIF_READ` and a buffer of 0x55.
3. Read the block back. Today it reads all zeros. Expected: an error and the 0xAA untouched, or at
   least not zeros.
4. Send INQUIRY with flags 0. Expected `scsi_Actual = 0` and an error; today it is 36 and success.
5. Send WRITE(10) of 2 blocks with `scsi_Length = 512`. Expected: an error; today the second block is
   zeros.

**Fix direction:** on a phase/direction mismatch, or a request for data past the buffer, abort:
assert ATN and send ABORT, or reset the bus. Return `HFERR_Phase` and count only the bytes that really
moved.

## Medium

### M1. The LUN still overwrites byte 1 of every caller CDB below $C0, including on LUN 0 (certain)
**Where:** `dataflyer.c:368`.

**Assumption:** in every opcode below $C0, bits 5-7 of byte 1 are the SCSI-1/2 LUN field. For LUN 0
units the driver **clears** them.

**Breaks with:**
- SEND DIAGNOSTIC $1D: SELF-TEST CODE is bits 7-5. A background self-test (1/2) becomes code 0.
- READ/WRITE/VERIFY (10/12/16): RDPROTECT/WRPROTECT.
- ATA PASS-THROUGH $A1/$85: MULTIPLE_COUNT.
- READ/WRITE BUFFER $3C/$3B: MODE SPECIFIC (SPC-4).
- SANITIZE $48: bit 7 is IMMED; clearing it makes the command run synchronously, which then hits H1.
- Vendor commands outside $C0-$FF (group-0 vendor slots, the reserved group 3 $60-$7F, some $A0-$BF):
  they get the LUN ORed in.

**Symptom:** a different command from the one the caller built.

**Test:** `CDBPASS`. Run it with a ZuluSCSI debug log on (`zululog.txt` prints every CDB), or with
WinUAE SCSI logging:
1. Send HD_SCSICMD TEST UNIT READY with byte 1 = $E0.
2. Send INQUIRY with byte 1 = $20 (on unit id, LUN 0).
3. Check the log: byte 1 must arrive unchanged.

**Fix direction:**
- For LUN 0, never touch byte 1.
- For LUN > 0, either OR in the LUN only on CDBs the driver builds itself, or select with ATN and send
  IDENTIFY ($80 | LUN), which is the SCSI-2 way. With IDENTIFY, no CDB LUN is needed.

### M2. LUNs are addressed only through the CDB; no IDENTIFY is sent (suspect: depends on the target)
**Where:**
- `dataflyer.c:198-200` (selection without ATN)
- `dataflyer.c:368`
- `dataflyer.c:594-598` (present = qualifier 0)

**Assumption:** the target decodes the LUN from CDB byte 1.

**Breaks with:**
- SCSI-1 drives that ignore the LUN field.
- SCSI-3+ targets, for which those bits are reserved: they address LUN 0 when no IDENTIFY comes.

Either kind answers INQUIRY for LUN 1-7 with LUN 0's data.

**Symptom:**
- Phantom units id+10 .. id+70, each a copy of the real disk.
- HDToolBox lists 8 copies of the drive.
- Mounting a partition through two of them corrupts it.

`RDBMount` scans LUN 0 only (`rdbmount.c:37`), so it is not affected.

**Test:** `LUNDUP`. For each present id, open units id+10*k for k = 1..7. For every unit that opens,
compare it with unit id:
- INQUIRY (vendor, product, serial if present);
- READ CAPACITY;
- a CRC of block 0.

Flag identical ones as "phantom LUN". Run on ZuluSCSI and on any vintage drive.

### M3. `start_task` / `df_open` races on concurrent first opens (certain code; low-medium likelihood)
**Where:** `dataflyer.c:1005-1026` and `dataflyer.c:1108-1124`.

**Assumption:** only one task ever runs the first `OpenDevice`.

**What happens in `start_task`:**
1. The first opener calls `AddTask` and then `Wait`s, which breaks exec's Forbid.
2. The driver task (priority 1) still has to set `cmdport`.
3. Meanwhile a second opener with higher priority runs. A DOS handler at priority 10 is enough, e.g.
   two partitions mounted with ACTIVATE at once.
4. It finds `cmdport == NULL`, `memset`s the **live** static `tc` and calls `AddTask` again.
5. Result: the task list is corrupted and the machine crashes.

**What happens in `df_open`:** two first opens of the same never-opened unit both allocate and probe.
The second overwrites `units[]`. The first opener's unit becomes an orphan:
- `df_ours` fails for it, so every request returns `TDERR_BadUnitNum`;
- `CloseDevice` does not decrement its count;
- it is never polled for changes.

**Test:** `RACEOPEN`, on a fresh boot, before anything else opens dataflyer.device. Start 4 child tasks
at priority 10. They wait on one shared signal, then all `OpenDevice` the same unit at once. Then each
does a `CMD_READ` of block 0. Expected: 4 successes, no crash, a consistent `unit_OpenCnt`.

**Fix direction:** a static "starting" flag, or do the start and the unit creation under a semaphore,
with a re-check after the `Wait`.

### M4. Probing in the caller's context spins under exec's Forbid (suspect: relies on OpenDevice calling Open under Forbid)
**Where:**
- `dataflyer.c:141` (no sleep outside the driver task)
- `dataflyer.c:1117` (`unit_probe` from `df_open`)
- `ide.c:363-384` and `ide.c:574` (takeover IDENTIFY: `T_PROBE` 1 s, `T_BUSY` 20 s)

**Assumption:** probes are short.

**Breaks with:**
- An absent id: 250 ms of frozen multitasking per open. Only the 3 s absent cache limits this, e.g.
  for HDToolBox scanning ids x LUNs.
- A target slow to answer INQUIRY: up to 10 s.
- A slow or absent IDE slave at the takeover: up to 1 s, or 20 s.

The README's "nothing is Forbid()den during a command" is not true for these commands.

**Test:** `OPENLAT`. A ticker task at priority 0 timestamps every 10 ms with timer.device and records
the largest gap while:
1. flysuite opens every absent id once;
2. it opens them again more than 3 s later;
3. it opens absent LUNs.

Report the largest gap. `tools/tick.c` may already be most of this.

### M5. scsi.device is left running for change interrupts added before the takeover (suspect)
**Where:**
- `ide.c:490-493` (TD_ADDCHANGEINT / TD_REMCHANGEINT on pre-takeover units go to the old BeginIO)
- `dataflyer.c:925-934` (the poller sees only our own `chgints`)

**Assumption:** scsi.device does nothing more on its own.

**Breaks with:** an IDE ATAPI CD mounted through scsi.device unit 1 before dataflyer.device loads,
which OS 3.2 does at boot. Two things go wrong:

1. That file system's change interrupt never fires again: scsi.device cannot see the port, and our
   poller does not poll the unit. A disc swap is noticed only if the file system itself polls
   `TD_CHANGESTATE`.
2. If OS 3.2's scsi.device polls removable media from its own task, it now writes the task-file
   registers. When the port is switched to SCSI, those addresses are the 53C80's registers. That is a
   collision outside `buslock`.

**Test:** `OLDCHG`.
1. Boot with CD0: on scsi.device unit 1 (ATAPI), then open dataflyer.device.
2. Swap the disc. CD0: must notice within a few seconds (`Info`, or `DiskChange`-free re-read).
3. Run a 10-minute SCSI read/verify loop while CD0: is mounted and changing.
4. Read `DF_DIAG` `bad_count`. Watch for any SCSI error during the loop.

### M6. CMD_UPDATE skips the flush on every "removable" unit (certain)
**Where:** `dataflyer.c:812`, together with `ide.c:388`.

**Assumption:** a removable unit has no write cache, or is a CD.

**Breaks with:**
- CompactFlash cards and IBM Microdrives: their IDENTIFY word 0 has bit 7 set (e.g. $848A), so they
  are marked removable and never get FLUSH CACHE. The Microdrive has a real write cache.
- SCSI MO and ZIP drives with write caches.

**Symptom:** data lost if the power goes off after FFS believes it has flushed.

**Test:** `FLUSH`. Read DF_STATS, send `CMD_UPDATE` to unit 100 (the CF), read DF_STATS again.
`cmds` must go up by 1; today it goes up by 0 on a CF. Do the same on a removable SCSI unit.

**Fix direction:** skip only for devtype 5 (CD-ROM), or send the flush and ignore ILLEGAL REQUEST.

### M7. run_cmd: the phase loop has no overall bound, the REQ wait ignores BSY, and messages are parsed one byte at a time (certain; low likelihood)
**Where:** `dataflyer.c:352-409`, `dataflyer.c:355`, `dataflyer.c:394-402`.

**What goes wrong:**
- **Endless 10 s cycles.** `dma_in`/`dma_out` can return 0 progress after a `drq_wait` timeout. The
  loop then goes round again (REQ still up, same phase), forever, 10 s per pass, holding `buslock`.
  This one does count timeouts.
- **Unexpected bus free.** The REQ wait does not stop when BSY drops. A disconnect, a target that
  drops BSY after STATUS without COMMAND COMPLETE, or a reset costs 10 s before the driver notices.
- **Multi-byte messages.** An EXTENDED MESSAGE ($01 len code ...) is read byte by byte. A $00 inside
  it, e.g. an SDTR offset of 0, is taken as COMMAND COMPLETE. The driver then returns while the target
  is still mid-message, and the bus is left hung (H1).
- **RESTORE POINTERS ($03) is ignored.** Re-sent data is appended after the data already received.
- **DISCONNECT ($04) costs 10 s and the command is lost.** Without IDENTIFY a target should not
  disconnect, but this matters if M1 moves to IDENTIFY with the disconnect bit set.

**Test:** these need a misbehaving target. A Pi or Arduino target emulator, or a patched ZuluSCSI
build, would do. In flysuite, the most you can do is check the counters: after every test step,
`DF_STATS timeouts == 0`, and no request takes longer than 2 s.

### M8. HD_SCSICMD reports every bus-level failure as `HFERR_SelTimeout` (certain)
**Where:** `dataflyer.c:708-711`, `dataflyer.c:413-416`, and `atapi_cmd`, which returns -1 for every
timeout.

**What goes wrong:**
- A REQ/ACK timeout in the middle of a command, an unexpected phase, or an ATAPI time-out all look
  like "no device at this id".
- A status byte that was received is thrown away if the MESSAGE IN after it fails.

HDToolBox and scanning tools then hide a present but sick device.

**Test:** part of H2 and M7. Once they are fixed, assert that a mid-command failure returns
`HFERR_Phase` or `HFERR_DMA`, not 46 (`HFERR_SelTimeout`).

### M9. HD_SCSICMD: `scsi_CmdLength` is never checked against the CDB group (certain)
**Where:**
- `dataflyer.c:347` (reads `cdb[0..1]` whatever the length)
- `dataflyer.c:368-369` (zero-pads)
- `dataflyer.c:433`
- `dataflyer.c:698` (only `> 16` is refused; 0 is allowed)
- `dataflyer.c:705` (`scsi_CmdActual = scsi_CmdLength`)

**What goes wrong:**
- **Too short.** A CDB shorter than its group length (6/10/10/12/16 for groups 0/1-2/4/5) is
  silently zero-padded. INQUIRY with CmdLength 4 gets allocation length 0, returns no data and
  status GOOD.
- **Too long.** The extra bytes are never sent, yet `scsi_CmdActual` says they were.
- **Length 0** with a NULL `scsi_Command` reads address 0 and sends what it finds there.

**Test:** `CDBLEN`:
- INQUIRY with CmdLength 4: expect an error (BADLENGTH), not GOOD with `Actual = 0`.
- READ(10) with CmdLength 12: expect `scsi_CmdActual = 10`.
- CmdLength 0: expect BADLENGTH.

## Low

### L1. A `medium_in` bus error counts as "medium gone" (certain)
**Where:** `dataflyer.c:902`.

A failed TEST UNIT READY (`st < 0`: select timeout, target busy) counts as no medium. That gives two
spurious changes, gone and then back. Each one bumps `changes`, clears `bsize` and calls
`Cause()`, so the file system re-mounts.

**Test:** none without fault injection. Once H1 is fixed, it falls out of `SLOWCMD`: no change
interrupt may fire during a long command on another id.

### L2. Block sizes that are not a power of two (certain)
**Where:** `dataflyer.c:656-670`.

The shift is floor(log2 bs), so with bs = 520 or 2352 the LBA comes out wrong whenever
`lo % bs == 0`. `CHUNK` (64 KB) is not a multiple of bs, so `nblk * bs != want`, `got < want`, and the
request fails with `TDERR_NotSpecified`.

**Test:** with the H3 hardfile at 520 bytes:
- `CMD_READ` offset 520*3, len 520: compare with HD_SCSICMD READ(10) LBA 3.
- `CMD_READ` of 130 KB.

**Fix direction:** refuse such units for CMD_READ/WRITE, or divide properly.

### L3. `rw` leaves `io_Actual` at 0 after a status error (certain)
**Where:** `dataflyer.c:681`.

On a status error the function returns before `io_Actual = done`, so the chunks that did succeed are
not reported. The short-transfer path at `dataflyer.c:685` does set it.

**Test:** `CMD_READ` of 128 KB starting 130 blocks before the end. Expect `io_Actual = 65536` with an
error. Today it is 0.

### L4. TD_PROTSTATUS is always 0 (certain)
**Where:** `dataflyer.c:856`.

CD-ROMs and read-only ZuluSCSI images report "writable".

**Test:** `TD_PROTSTATUS` on a CD unit must be non-zero.

**Fix direction:** devtype 5, or the WP bit from MODE SENSE.

### L5. Shared static buffers between the opener's task and the driver task (certain)
**Where:** `sense_buf` (`dataflyer.c:84`) and `inq` (`dataflyer.c:587`).

`unit_probe` runs in the opener's task (from `df_open`) and in the driver task (from `rw` and
`geometry`). Between one task's command and its reading of the buffer, the other task can overwrite
it. That gives a wrong error mapping or a wrong devtype/removable flag. The window is narrow.

### L6. No recovery on the IDE side (certain code)
**Where:** `ide.c:286-307`, `ide.c:149`, `ide.c:574-577`.

- No SRST (device control bit 2) and no ATAPI DEVICE RESET after a time-out. A drive left BSY or in
  DRQ makes every later command wait 20 s and fail.
- If IDENTIFY fails at the takeover (drive slow or busy), `ide_units[k]` stays NULL for good. A
  partition already mounted through scsi.device unit 0 then gets `TDERR_BadUnitNum` until reboot, and
  nothing ever probes the drive again.
- `ata_xfer` reads do not check the status after the last sector.

### L7. Gaps in the ATA translation (certain)
**Where:** `ide.c:179-271`.

- `ide.c:260`: if `scsi_Length` is shorter than the CDB's count, the transfer is truncated and the
  status is still GOOD.
- `ide.c:206`: INQUIRY with allocation length 0 returns 36 bytes.
- `ide.c:218`: the MODE SENSE page-control bits are ignored, so "changeable values" returns the
  current ones.
- `ide.c:187`: VERIFY is a no-op that succeeds, so an HDToolBox verify passes instantly.
- `ide.c:285`: 16-byte CDBs to ATAPI are cut to 12 without an error. Devices with 16-byte packets
  (IDENTIFY PACKET word 0 bits 1-0 = 01) are not supported.

### L8. Pseudo-DMA writes: the last byte, the extra byte, and runs on by default (suspect)
**Where:** `dataflyer.c:316-338`, `dataflyer.c:86`, `start.S:141-175`.

- **Byte count.** A byte written into the chip's latch counts as sent. If the target changes phase
  early, `scsi_Actual` is one too high.
- **The extra byte.** After a `drq_wait` time-out, the extra `DMAPORT = 0` write lands on a chip that
  is not ready. If the card holds writes the way it holds reads, the CPU freezes.
- **Write runs are on by default** (`opts = 1`), though `start.S` calls them "an experiment". If a
  target drops REQ in the middle of a 256-byte run, there are two possibilities, depending on the card:
  - the CPU is held with interrupts off, for as long as an SD write can stall (serial, audio and timer
    losses);
  - or bytes are lost and the rest of the block is zero-padded, with status GOOD: silent corruption.

**Test:** `WSOAK`. Write and verify 200 MB in random lengths of 1-128 blocks at random scratch offsets.
Run it with `OPTS=1` and again with `OPTS=0`. Compare every block, and record the largest ticker gap
(from M4's ticker) during the writes.

### L9. Selection times out without the selection-abort check (suspect)
**Where:** `dataflyer.c:201-204`.

On a timeout the driver drops SEL at once, without first releasing the data bus and checking BSY
again after about 200 us. A target that answers just late is left selected and holding BSY. Combined
with H1, the bus is hung.

### L10. The RDBMount core can overflow its buffer (tool; certain)
**Where:** `tools/rdbmountcore.h:52`, `:59`, `:71`.

The buffer is 1024 bytes, but `rdb_BlockBytes` up to 4096 is accepted and that many bytes are read
into it. That is a heap overflow for an RDB with 2048- or 4096-byte blocks. It is hard to reach
through dataflyer.device, because the 512-byte RDSK search reads are refused on a 2048-byte unit.
RDBMount takes any device name, though, so it is reachable through other devices.

The same 512-byte search means RDBMount never finds an RDB on 2048-byte MO media.

## Status in 1.0.5 (branch fix/1.0.5)

Fixed: H1 (per-opcode budgets, bus reset on a time-out, CMD_RESET), H2, H3, H4, H5, H6, M1, M3, M6,
M8, L2, L4, L10, plus the IDE short-buffer read. M7's "endless 10 s cycles" went with H1 (a DMA
REQUEST time-out ends the command and resets the bus).

Not changed in 1.0.5, and why:

- **M2** (no IDENTIFY for LUNs): needs a target with real LUNs to see what breaks; WinUAE and the
  ZuluSCSI answer LUN 0 only. Untestable here, left as it is.
- **M4** (probes spin under Forbid): by design - a probe from OpenDevice has no task to sleep in,
  and the 3 s absent-id cache bounds the cost. Documented, not changed.
- **M5** (scsi.device left running for change interrupts added before the takeover): needs a
  design for the pre-takeover units' change interrupts; the OS 3.2 CD0 case works through
  TD_CHANGESTATE polling in the file system. Open.
- **M7** (the rest: BSY ignored by the REQ wait, one-byte message parsing, RESTORE POINTERS,
  DISCONNECT): needs a misbehaving target to show; without IDENTIFY no target disconnects. Open.
- **M9** (scsi_CmdLength not checked against the CDB group): a change in what a caller gets for a
  malformed request; left for a release of its own.
- **L1** (a medium_in bus error counts as "medium gone"): falls out of H1 on a real slow disk;
  not seen yet.
- **L3** was fixed with H5 (rw sets io_Actual on every exit).
- **L5** (shared static sense/INQUIRY buffers between the opener's and the driver's task): the
  window is a few microseconds and the result a wrong error code once; left.
- **L6** (no IDE-side reset, IDENTIFY retry): needs hardware that misbehaves to test against.
  CMD_RESET does nothing for an IDE unit for the same reason.
- **L7** (ATA translation gaps): cosmetic for the callers that exist (HDToolBox, FFS).
- **L8** (write runs: the last byte, the extra byte, runs by default): H3 now limits runs to whole
  blocks of a plain WRITE the target must take in full; the extra byte after a time-out is gone
  (dma_out leaves at once). Whether the card holds a write to a chip that is not ready stays
  unknown (suspect); DF_OPTS=0 turns the write runs off.
- **L9** (selection without the abort check): real-hardware behaviour, never seen; H1's reset
  now frees a bus a late target left hung.

## The one-off stall ("reads wedged after a large write, no timeouts counted")

What the code allows, and what each case would look like in `flystat` if it happens again. `DF_STATS`
runs in the caller's task, so flystat works even while the driver task is stuck.

| Cause | Machine responsive? | `timeouts` | Counter that moves |
|---|---|---|---|
| The target answers slowly, each wait under 10 s (e.g. ZuluSCSI SD garbage collection after a big write) | yes | 0 | `polls[W_REQ]` and `sleeps` grow fast |
| Byte-wise drain or padding, i.e. a length mismatch (H4/H6) | yes, crawling | 0 | `polls[W_ACK]` grows |
| CPU held in a blind run (H3/L8) | **no**, total freeze | n/a | none |
| ATAPI loop (H2) | barely (priority 1 spin) | 0 | none |
| A request never answered / semaphore | yes | 0 | none; the driver task sits in `Wait` |

I found no path that loses a request or leaves `buslock` held. So if it happens again with the
machine responsive and no counter moving, look at the file system rather than the driver.

## What looked solid

- **The 1.0.4 vendor fix itself.** Opcodes $C0-$FF are passed untouched.
- **REQUEST SENSE.** The LUN and allocation-length bytes are right. Autosense runs only on CHECK
  CONDITION, and its length is limited to 255 and to the caller's buffer.
- **DATA IN overruns** (SCSI and ATAPI) are drained, never written past `scsi_Length`.
- **Every copy is bounded:** sense, INQUIRY (36), READ CAPACITY (8), the ATA MODE SENSE build (60 of
  64 bytes), DF_DIAG/DF_STATS/IRQPROBE length checks.
- **No memory assumptions.** No DMA, so no MEMF_24BITDMA or word-alignment needs.
  `dg_BufMemType = MEMF_PUBLIC`, chip RAM is fine, and odd buffers are fine on 68020+ (`move.l`/`move.w`
  in `df_idein`/`df_ideout`).
- **TD64/NSD offsets.**
  - The 64-bit offset to LBA conversion is right, and anything past 2 TB is refused with
    `IOERR_BADADDRESS`.
  - Partial-block offsets and lengths are refused.
  - 64 KB chunks, and the last chunk, are right for power-of-two block sizes.
  - `io_Actual` is read as the high half before it is cleared.
- **The 2048-byte CD path,** once READ CAPACITY has worked (but see H4).
- **IDE details.**
  - The IDENTIFY byte swap, the model and firmware strings, LBA vs CHS.
  - LBA48 detection (word 83 & $C400 == $4400) and the size from words 100-103, capped at
    $FFFFFFFF.
  - The LBA28/48 switch at `lba + n > $0FFFFFFF`, and the high-before-low register order.
  - A count of 256 encoded as 0.
  - READ(6): LUN masked off, length 0 = 256.
  - Writes word by word.
- **ATAPI.** Byte order is consistent between the packet, the 512-byte runs and the word path. An odd
  final byte count is handled, and bytes past the buffer are drained.
- **Port ownership.**
  - Every switch to SCSI and every IDE access happens under `buslock`, and `SEL_IDE()` comes back after
    every SCSI command and in IRQPROBE.
  - Quick-path commands (TD_CHANGENUM, PROTSTATUS, DEVICEQUERY, no-ops, DF_*) never touch the port.
  - The poller runs in the driver task, so it never races normal I/O.
- **Waits.**
  - Each 53C80/IDE wait is bounded on its own.
  - Sleeping happens only in the driver task.
  - CIA-read timing is the same on every CPU, and preemption only makes timeouts longer, never shorter.
- **Selection.** The selection timeout (250 ms) plus the 3 s absent-id cache works.
- **Change interrupts.** The TD_ADDCHANGEINT / TD_REMCHANGEINT / AbortIO lifecycle is right, including
  REMCHANGEINT with the same request (handled on the quick path, so the linked node is never sent
  through PutMsg).
- **Device bookkeeping.**
  - OpenDevice/CloseDevice counts are right, including the scsi.device units 0/1 opened through
    `sd_open`.
  - Expunge can never run after the takeover, by design.
  - NSCMD_DEVICEQUERY's contents are right.
- **Unit numbers.** `id > 6 || lun > 7` keeps `units[]` in range; units 100/101 are handled before
  that check.
- **The takeover's drain** (one read per unit through the old BeginIO), with
  `ide_mapped` holding requests back until `taken` is set.
